# 技术方案：页面状态保持与后台任务持续

## 1. 需求概述

当前 go-stock React 前端使用条件渲染（`currentView === 'xxx' && <Component />`）实现页面切换，导致页面切换时组件被完全卸载销毁，引发以下问题：

- 页面本地状态丢失（useState、useRef）
- 进行中的异步任务（如 AI 流式分析）被中断
- Wails 事件监听（EventsOn）在 useEffect 清理中被注销，后端推送数据丢失
- 重新进入页面需重新加载数据，体验不连贯

**核心目标**：实现页面组件 Keep-Alive，切换页面时不销毁已加载组件，而是通过隐藏/显示机制保持组件存活。

详细需求见：[需求-页面状态保持与后台任务持续-20260319.md](./需求-页面状态保持与后台任务持续-20260319.md)

## 2. 技术方案概述

采用 **visitedViews 懒加载 + CSS display 切换** 方案，核心思路：

1. 引入 `visitedViews` 状态（Set 类型），追踪用户已访问过的页面
2. 当 `currentView` 变化时，自动将新页面加入 `visitedViews`
3. 渲染时，只有 `visitedViews` 中包含的页面才真正挂载到 DOM
4. 通过 CSS `display: none/block` 控制当前活跃页面的可见性
5. 已访问过的页面永不卸载，状态和事件监听自然保持

这种方案实现了：
- **懒加载**：首次访问页面时才挂载组件，避免初始加载所有页面
- **永不卸载**：页面一旦挂载就保持存活，切走时只是隐藏
- **最小改动**：改动完全集中在 App.tsx，无需修改任何子组件代码

## 3. 详细设计

### 3.1 visitedViews 状态管理

引入一个 `Set<string>` 类型的状态来追踪已访问页面：

```typescript
const [visitedViews, setVisitedViews] = useState<Set<string>>(() => new Set(['dashboard']));
```

**设计要点**：
- 初始值包含 `'dashboard'`，因为这是默认首页，应用启动即挂载
- 使用 Set 而非数组，便于 O(1) 的存在性检查
- 使用惰性初始化（函数形式）避免每次渲染都创建新 Set

**更新逻辑**：当 currentView 变化时，将新视图加入 visitedViews：

```typescript
useEffect(() => {
  setVisitedViews(prev => {
    if (prev.has(currentView)) return prev; // 已存在则不更新，避免不必要的 re-render
    const next = new Set(prev);
    next.add(currentView);
    return next;
  });
}, [currentView]);
```

### 3.2 渲染逻辑改造（从条件渲染到 display 切换）

**改造前**（条件渲染，会卸载组件）：
```tsx
{currentView === 'dashboard' && <Dashboard />}
{currentView === 'watchlist' && <Watchlist />}
{currentView === 'aianalysis' && <AIAnalysis />}
// ... 其他页面
```

**改造后**（display 切换，保持组件存活）：
```tsx
<div style={{ display: currentView === 'dashboard' ? 'block' : 'none' }}>
  {visitedViews.has('dashboard') && <Dashboard />}
</div>
<div style={{ display: currentView === 'watchlist' ? 'block' : 'none' }}>
  {visitedViews.has('watchlist') && <Watchlist />}
</div>
<div style={{ display: currentView === 'aianalysis' ? 'block' : 'none' }}>
  {visitedViews.has('aianalysis') && <AIAnalysis />}
</div>
// ... 其他页面
```

**渲染行为分析**：

| 场景 | visitedViews 包含 | currentView 是否匹配 | 结果 |
|------|:----------------:|:------------------:|------|
| 从未访问 | ❌ | ❌ | 不渲染（空 div） |
| 首次访问 | ✅（刚加入） | ✅ | 挂载并显示 |
| 切走后 | ✅ | ❌ | 隐藏但保持挂载 |
| 切回时 | ✅ | ✅ | 显示（状态保持） |

### 3.3 事件监听行为变化说明

**为什么 Keep-Alive 后事件监听自然保持？**

以 AIAnalysis 组件的流式分析为例，当前代码结构：

```typescript
// AIAnalysis 组件内部
useEffect(() => {
  const cleanup = EventsOn('newChatStream', (data) => {
    setAnalysisContent(prev => prev + data);
  });
  
  return () => {
    EventsOff('newChatStream'); // 组件卸载时清理
  };
}, []);
```

**条件渲染时的问题**：
1. 用户在 AIAnalysis 发起分析
2. 切换到 Watchlist → AIAnalysis 组件卸载 → useEffect 返回的清理函数执行 → EventsOff 注销监听
3. 后端继续推送 newChatStream 事件，但前端已无监听者，数据丢失
4. 切回 AIAnalysis → 组件重新挂载 → 重新注册监听，但之前的数据已丢失

**Keep-Alive 后的行为**：
1. 用户在 AIAnalysis 发起分析
2. 切换到 Watchlist → AIAnalysis 组件只是隐藏（display:none），**不卸载**
3. useEffect 的清理函数**不执行**，EventsOn 监听保持活跃
4. 后端推送 newChatStream，监听函数正常触发，setAnalysisContent 正常更新状态
5. 切回 AIAnalysis → 组件显示，用户看到最新的分析进度或完成结果

**核心原理**：React 组件的 useEffect 清理函数只在组件卸载时执行。display:none 不会卸载组件，因此事件监听、定时器等副作用自然保持运行。

### 5.2 辅助工具函数（可选优化）

如果觉得重复代码过多，可以提取一个辅助组件：

```tsx
interface KeepAliveViewProps {
  name: string;
  currentView: string;
  visitedViews: Set<string>;
  children: React.ReactNode;
}

function KeepAliveView({ name, currentView, visitedViews, children }: KeepAliveViewProps) {
  return (
    <div style={{ display: currentView === name ? 'block' : 'none' }}>
      {visitedViews.has(name) && children}
    </div>
  );
}

// 使用方式
<KeepAliveView name="dashboard" currentView={currentView} visitedViews={visitedViews}>
  <Dashboard />
</KeepAliveView>
```

此优化为可选项，初期可直接使用内联写法，后续根据需要重构。

## 6. 性能与风险评估

### 6.1 内存影响分析

**7 个页面常驻的开销**：

| 页面组件 | 主要状态数据 | 估计内存占用 |
|---------|-------------|-------------|
| Dashboard | 新闻列表、市场数据 | 约 200KB-500KB |
| Watchlist | 股票列表、价格数据 | 约 100KB-300KB |
| AIAnalysis | 分析文本、历史记录 | 约 100KB-1MB（取决于分析量）|
| StockFilter | 筛选条件、结果列表 | 约 100KB-500KB |
| Settings | 表单状态 | 约 10KB |
| MoneyFlow | 资金流向数据 | 约 100KB-300KB |
| AboutUs | 静态内容 | 约 5KB |
| LongTigerRank | 龙虎榜数据 | 约 100KB-300KB |

**总计**：约 700KB - 3MB（取决于用户使用深度）

**评估结论**：现代设备内存充足，此量级的内存占用完全可接受。相比之下，每次切换页面重新加载数据的网络开销和用户等待时间是更大的代价。

### 6.2 隐藏组件的事件监听和 setState 影响

**事件监听**：
- 隐藏的组件仍会接收 Wails 事件并执行回调
- 这正是我们需要的行为（后台任务持续）
- 开销：事件回调的 JS 执行时间，通常在毫秒级，可忽略

**setState 调用**：
- 隐藏组件调用 setState 会触发组件重新渲染
- 但 `display: none` 的组件不参与浏览器的布局和绘制阶段
- 开销：仅 React Virtual DOM diff，无实际 DOM 重绘
- 风险：如果隐藏组件频繁 setState（如每秒多次价格更新），可能有轻微性能影响

**优化建议**（如遇性能问题再实施）：
- 可在组件内部增加 `isVisible` prop，高频更新场景下仅在可见时才更新 UI
- 但初期建议不做此优化，保持简单，实测后再决定

### 6.3 潜在风险和缓解措施

| 风险 | 可能性 | 影响 | 缓解措施 |
|-----|:-----:|-----|---------|
| 内存泄漏（组件永不卸载） | 低 | 中 | 定期检查内存占用；极端场景可考虑 LRU 策略卸载最久未访问的页面 |
| 隐藏组件的定时器持续运行 | 中 | 低 | 这是预期行为；如有不需要的定时器，应在组件内部按业务需求控制 |
| 外层 div 影响样式布局 | 低 | 低 | 包裹 div 仅用于 display 控制，不添加额外样式；如有问题可调整为 Fragment + CSS class |
| 键盘焦点管理 | 低 | 低 | 隐藏组件内的表单元素不会获取焦点（display:none 元素不可聚焦） |
