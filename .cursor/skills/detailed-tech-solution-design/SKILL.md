# 详细技术方案设计

作为技术 PM，基于 `feature/` 下已对焦清楚的产品需求文档，产出**可被 AI Coding 严格按序执行**的详细技术方案。要求：不遗漏、事无巨细、跨域协议同步定义、开发步骤与执行主体明确，方案中深入代码级并写出代码或伪代码。

## 何时使用

- `feature/` 下已有**澄清后需求明细**定稿的需求文档（对焦完成）。
- 用户明确要求「写技术方案」「设计技术方案」「出技术方案文档」或「按需求做实现设计」。

若需求尚未对焦（待产品确认未关闭、澄清后需求明细未补全），**先提示用户**：请先完成需求澄清，或使用需求澄清技能产出定稿需求后再进入本阶段。

---

## 执行流程

按顺序执行，不跳过。

### 1. 确认输入与前置条件

- 读取 `feature/` 下与本需求对应的需求文档（如 `需求-{主题}-{日期}.md`）。
- 确认文档中「待产品确认」已全部关闭、「澄清后需求明细」已补全且可执行。
- 若未满足：明确列出缺失项，**请用户回到上一步与产品对焦**，不猜测、不代产品做业务决策。

### 2. 理解项目与代码结构

- 扫读仓库根、主要模块（如 `frontend/`、`backend/`、`build/`）、入口与核心领域。
- 若有 `通识.md`、`README.md`、`docs/`，提炼与本期需求相关的架构与术语。
- **定位与需求相关的代码**：涉及的文件、包、接口、数据模型、路由、组件；列出清单并在方案中引用具体路径与符号。

### 3. 技术方案正文（事无巨细）

产出一份技术方案文档，结构参考 [technical-solution-template.md](technical-solution-template.md)，并满足：

- **范围与目标**：与需求文档中的目标、澄清后需求明细一一对应，不遗漏任何功能点。
- **架构与模块**：模块划分、依赖关系、目录/包结构；若有**技术选型或架构取舍**（如新库、新通信方式、存储方案等），**暂停并直接询问用户决策**，在方案中记录结论与理由。
- **数据与接口**：数据模型变更、API 变更、请求/响应格式；**与其他域（后端、第三方、上下游）的对接协议**在本节或独立小节中**同时定义**：接口路径、方法、鉴权、请求/响应体、错误码、兼容与版本策略等，避免开发阶段再补协议。
- **代码级设计**：对关键逻辑、状态流、边界条件，在技术方案中**直接写出代码或伪代码**（可贴片段或伪代码块），深入到足以让 AI Coding 无歧义实现；涉及的文件路径、函数名、关键参数与返回值要具体。若在写代码时发现需求含糊或与现有实现冲突，**在方案中标注「需与产品再对焦」并列出问题，请用户回到上一步与产品确认**。
- **UI/前端**：若涉及页面、组件、路由、样式，写出组件树、路由表变更、关键 class/变量与伪代码，与需求中的「涉及端/模块」对应。

### 4. 跨域/对外协议小节

- 集中列出本期涉及的**所有对外对接**：后端 API、第三方服务、前端与 Go 的 Wails 绑定等。
- 对每一项给出：协议形式（REST/事件/等）、端点或事件名、鉴权、请求/响应示例、错误码与重试策略。与「数据与接口」一致，不遗漏。

### 5. 开发步骤与执行顺序

- 将实现工作拆成**有序的开发步骤**（步骤 1、2、3…），保证依赖关系正确（例如：接口契约与模型先于调用方实现）。
- 每一步必须标明：
  - **执行主体**：**人** 或 **AI Coding**；
  - **输入**：依赖哪几步的产出或哪份文档；
  - **产出**：交付物（分支/文件/接口/文档）。
- 说明：**AI Coding 将严格按照本顺序执行**，不得跳步或并序除非方案中明确允许。

### 6. 输出与落位

- 在 `feature/` 下生成技术方案文档，命名与对应需求文档一致，并在末尾加上 `_技术方案`：即 `{需求文档文件名（不含 .md）}_技术方案.md`（如需求文档为 `需求-前端布局与样式改版-20250312.md`，则技术方案为 `需求-前端布局与样式改版-20250312_技术方案.md`）。
- 文档内注明：对应的需求文档路径、技术方案版本（可选）、以及「对 AI Coding：请严格按第 N 节开发步骤顺序实现」。

---

## 与需求文档的衔接

- 技术方案中的「需求依据」或「需求条目」应引用需求文档的章节与功能点（如 5.1、5.2）。
- 若在编写方案时发现需求文档存在遗漏或矛盾，在方案中单独列出「需与产品再对焦」项，并**建议用户回到需求澄清阶段**与产品确认后再更新技术方案。

---

## 架构或选型需用户决策时

遇到以下情况，**直接询问用户**，不在方案中自行拍板：

- 引入新技术栈、新依赖或新部署方式；
- 与现有架构不一致的通信/存储/安全方案；
- 多方案均可满足需求时的选型（在方案中简述选项与利弊后询问用户选择）。

将用户决策记录在技术方案中，并作为后续开发步骤的依据。

---

## 注意事项

- **不替产品做业务决策**：业务规则、文案、优先级以需求文档为准；不明确处标注并请用户与产品对焦。
- **不遗漏**：需求文档中每条澄清后需求明细都应有对应的方案设计与开发步骤。
- **协议先行**：跨域、前后端、第三方协议在技术方案阶段定稿，避免开发中反复改接口。
- **代码/伪代码到位**：关键路径必须有可执行的代码或伪代码，减少 AI Coding 理解偏差。
