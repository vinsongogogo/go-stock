# 需求澄清（技术 PM）

作为技术 PM，与产品对焦需求，在设计阶段把不明确处澄清。输出为 `feature/` 下的明细需求文档。**本过程为多轮对话**：每轮根据产品反馈更新「待产品确认」与「澄清后需求明细」，直至对焦清楚。

## 执行流程

按顺序执行，不跳过。

### 1. 理解项目组成

- 列出仓库根目录与主要模块（如 `backend/`、`frontend/`、`build/` 等）。
- 识别入口与核心领域：主程序入口、数据层、业务服务、前端页面/路由。
- 若存在 `README.md`、`docs/`，快速扫读以把握架构与术语。

### 2. 读取业务通识

- 优先查找并阅读 **`knowledge/common.md`**（项目通识，由自我优化技能在功能完成后维护）；若无，再查找 **`通识.md`**（仓库根或 `docs/通识.md`）。若均不存在，在后续文档中注明「当前无通识文件，建议补充」。
- 提炼与本次需求相关的业务概念、名词定义、现有能力边界（入口、谁调用、依赖、设计原因等）。

### 3. 对照需求分析代码

根据产品给出的需求描述：

- **定位相关代码**：接口/API、前端页面与组件、数据模型、关键业务函数。
- **梳理现有逻辑**：数据流、状态、权限、边界条件、错误处理。
- **对比需求与实现**：已实现 / 部分实现 / 未实现；与需求表述一致或存在偏差。

### 4. 列出不明确项

整理「需与产品确认」的问题，格式：

- **不明确点**：简短描述（如：XX 的边界条件是什么？）
- **当前实现/假设**：代码中现状或合理推断。
- **影响**：不澄清可能导致的范围、体验或技术风险。

分类建议：业务规则、交互细节、数据与权限、性能与量级、异常与降级。

### 5. 输出需求文档到 feature/

- 在项目下创建 **`feature/`** 目录（若不存在）。
- 文档命名：`feature/需求-{简短主题}-{日期或版本}.md`，例如 `feature/需求-自选股分组-20250312.md`。
- 文档结构使用 [requirements-template.md](requirements-template.md)，包含：需求概述、业务通识摘要、现状与代码结论、待澄清列表、澄清后的明细需求（可在澄清后补全）。

## 需求文档必备章节

- **需求概述**：一句话目标 + 背景/价值（可选）。
- **业务通识摘要**：与本期需求相关的名词、规则（来自 通识.md 或标注缺失）。
- **现状与代码结论**：相关模块、已实现能力、与需求差异。
- **待产品确认**：上一步的不明确项列表（含当前实现/假设与影响）。
- **澄清后需求明细**：按功能点/用户故事列出的可执行需求（可先留空，澄清后填写）。

## 多轮对焦

- 首轮：产出需求文档初稿（含「待产品确认」与可填的「澄清后需求明细」），交给产品确认。
- 后续轮次：根据产品回复逐条关闭或更新待确认项，补全「澄清后需求明细」；若产生新的不明确点，继续列入待确认并更新文档。
- **对焦完成的标志**：待产品确认列表为空或已全部有结论，且「澄清后需求明细」已补全、产品认可。

## 对焦完成后的下一步

当需求对焦清楚（待确认项已全部关闭、澄清后需求明细已定稿）时，**明确提示用户执行下一步**：

> 需求已对焦清楚，可进入下一阶段。请执行：
> 1. **生成技术方案**：基于本期需求做架构/模块设计、接口与数据变更、技术选型与风险说明。
> 2. **生成明细变更文档**：包含但不限于：
>    - 代码/模块变更清单与影响范围；
>    - 数据模型与接口变更说明；
>    - **与外域（第三方、上下游系统）的对接协议**：请求/响应格式、鉴权、错误码、兼容与版本策略等（若本期涉及外域对接）。

可提示用户说：「请根据 feature/需求-xxx 生成技术方案和明细变更文档」或类似表述，以触发下一阶段技能或任务。

## 注意事项

- 不替产品做业务决策；不明确处一律列入「待产品确认」，不猜测。
- 分析代码时引用具体路径与符号（文件、函数/接口名），便于产品与开发对齐。
- 若需求涉及多端（如桌面端/移动端）或多模块，在文档中分节说明各自范围与依赖。
