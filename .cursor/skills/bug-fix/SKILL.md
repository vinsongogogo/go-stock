# Bug Fix

## Workflow Overview

1. **辨明问题** — 准确理解现象与用户真实诉求  
2. **全链路分析** — 枚举可能原因并定位根因  
3. **实施修复** — 最小改动、可回滚  
4. **验证** — 复现场景通过 + 无回归  

---

## 1. 辨明问题

### 1.1 表面现象

- **复现步骤**：在什么操作/输入/环境下出现？若用户未给全，主动追问或从代码推断。
- **预期 vs 实际**：用户期望什么？当前实际表现是什么？（含报错文案、截图、接口返回等。）
- **环境**：分支、环境（dev/staging/prod）、浏览器/设备、相关配置或数据状态。

### 1.2 深层次含义

- **真实诉求**：用户说的“修好这个”背后，可能还包含“不要再在其他地方坏掉”“要能快速排查下次”等。
- **隐含假设**：用户可能默认了某些前提（例如“只有我会这样用”“数据一定是合法的”），若与实现不一致，需在修复或说明中体现。
- **影响范围**：仅当前页面/功能，还是会影响其他模块、下游或历史数据。

用一两句话在修复前写下「问题摘要」和「修复目标」，避免修偏。

---

## 2. 全链路分析

按可能出问题的层次列清单，再结合现象缩小范围：

| 层次 | 检查点 | 示例 |
|------|--------|------|
| **UI/交互** | 条件渲染、事件绑定、状态更新、权限/角色展示 | 按钮点了没反应、列表不刷新 |
| **前端逻辑/状态** | 本地状态、缓存、路由、表单校验 | 提交后仍显示旧数据、校验不触发 |
| **请求/协议** | URL、方法、请求体、请求头、CORS | 404、415、跨域、参数丢或错 |
| **后端接口** | 路由、鉴权、参数解析、业务逻辑、错误码 | 500、错误信息不对、结果不符合预期 |
| **数据/存储** | 库表、迁移、索引、事务、脏数据 | 查不到、重复、约束冲突 |
| **配置/环境** | 环境变量、特性开关、依赖版本、构建产物 | 仅某环境异常、依赖升级后坏 |
| **集成/依赖** | 第三方 API、消息队列、定时任务、上下游服务 | 超时、格式变化、顺序问题 |

**操作**：

- 根据现象先假设 1～3 个最可能原因，按优先级查代码/日志/配置。
- 能找到日志或错误栈时，从报错位置反推调用链和数据流。
- 若仍不确定，用最小复现（单接口、单页面、固定数据）做假设验证，再修。

---

## 3. 实施修复

- **最小改动**：只改导致当前问题的代码路径，避免顺手“顺便优化”引入新风险。
- **可回滚**：不删关键逻辑时优先用新增/条件分支；若必须改核心逻辑，注明原因并保留原逻辑注释或可快速还原的方式。
- **风格一致**：命名、错误处理、日志风格与项目现有代码保持一致。
- **改完即记**：在提交或回复中简短说明「根因 + 修改点 + 为何这样改」。

---

## 4. 验证

### 4.1 问题修复验证

- 用用户描述的步骤（或等价的最小步骤）再跑一遍，确认：**预期行为出现、异常/报错消失**。
- 若有多种合法输入或环境，至少覆盖：原先失败的那一类 + 一种正常 case，避免修 A 坏 B。

### 4.2 回归与影响面

- **相关测试**：若有单测/集成测覆盖该路径，必须跑过并全部通过。
- **影响面**：本次改动涉及到的模块（调用方、被调用方、配置）在脑中过一遍，有自动化测试则跑全量或相关子集。

### 4.3 结果反馈

向用户说明：

- 根因是什么（一句话）。
- 做了哪些修改（文件/逻辑简述）。
- 验证结果：复现场景已通过，并已执行哪些回归检查。
- 若存在限制或后续建议（例如需清缓存、需改配置、建议加监控），一并说明。

---

## 检查清单（修复前可默念）

- [ ] 复现步骤与预期/实际已弄清，必要时已追问用户
- [ ] 已考虑用户深层次诉求与隐含假设
- [ ] 已做全链路可能性分析并锁定根因（或最可能 1～2 个）
- [ ] 修复范围最小、可回滚、风格一致
- [ ] 已用原复现路径验证通过
- [ ] 已跑相关/回归测试并确认无新问题
- [ ] 已向用户反馈根因、修改点与验证结果
