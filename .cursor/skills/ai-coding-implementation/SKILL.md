# AI Coding 实现

按照 `feature/` 下技术方案文档（`*_技术方案.md`）的「7. 开发步骤」严格按序执行实现，确保每一步执行到位；允许并行时创建子 agent 并发实现。全部步骤完成后做改动点核对与补充、单测与验证，通过后通知用户完成。

## 何时使用

- 用户指定或当前上下文中已有**技术方案文档**（如 `feature/需求-xxx-日期_技术方案.md`）。
- 用户要求「按技术方案实现」「AI Coding 实现」「执行技术方案」或类似表述。

若尚未有技术方案文档，先提示用户：请先使用「详细技术方案设计」技能产出技术方案，或提供技术方案文档路径。

---

## 输入与解析

### 0. 读取并应用自我优化沉淀（优先）

- 在按技术方案执行任何开发步骤之前，先读取 `.cursor/skills/self-optimization/corrections/` 下与实现相关的文件（若存在）：
  - `tech-implementation.md`（技术选型、写法、目录、命名等）
  - `workflow.md`（先列改动再改、是否跑测试等流程偏好）
  - `style-format.md`（代码风格、注释语言等）
- 将其中列出的「规则」作为本次实现的约束与偏好，贯穿 Phase 1～4；与技术方案冲突时以技术方案为准，必要时在通知中说明。

### 1. 确认技术方案文档

- 读取技术方案全文（通常来自 `feature/*_技术方案.md`）。
- 确认文档包含：
  - **7. 开发步骤与执行顺序**：表格含「步骤、内容简述、执行主体、输入依赖、产出」。
  - **5. 代码级设计**：各小节含「涉及文件」及代码/伪代码。
- 仅执行**执行主体为「AI Coding」**的步骤；执行主体为「人」的步骤在说明中标注，由用户自行完成。

### 2. 提取执行清单

- **步骤列表**：从「7. 开发步骤」表格按顺序得到步骤 1～N；若「内容简述」中出现「可与步骤 M 并行」，记录该步骤可与 M 并行。
- **改动点清单**：从「5. 代码级设计」各小节收集「涉及文件」；从「7. 开发步骤」表格收集每步「产出」。合并去重，作为最终核对清单（用于 Phase 4 验证）。

---

## Phase 1：按序执行开发步骤

- 严格按步骤 1 → 2 → … → N 的顺序执行；有**输入依赖**的步骤必须在其依赖步骤完成后执行。
- 对每一步（执行主体为 AI Coding）：
  1. 根据「内容简述」「输入依赖」「产出」和「5. 代码级设计」中对应小节，定位涉及的章节与代码/伪代码。
  2. 在对应文件中完成实现或修改，确保与方案中的路径、函数名、组件名、变量名一致。
  3. 若方案中注明「可与步骤 K 并行」且当前无未完成的依赖，可与步骤 K **并发**执行：使用子 agent（如 `mcp_task`）将「步骤 K」或「步骤 当前」作为独立任务下发，等待子 agent 完成后继续主流程；主流程中仍按顺序推进，仅对明确标注并行的步骤发起并发。
- **并行策略**：仅在「内容简述」明确写「可与步骤 N 并行」时发起子 agent；同一批可并行的步骤可一次性发起多个子 agent，主 agent 等待全部完成后再进入下一批顺序步骤。
- 每完成一步，在内部清单中标记该步「已完成」及对应产出文件，便于 Phase 4 核对。

---

## Phase 2：确保每步执行到位

- 单步完成后自检：
  - 该步「产出」列中的文件/目录是否已创建或修改。
  - 「5. 代码级设计」中与该步对应的小节（通过输入依赖、内容简述对应）所列「涉及文件」是否均已改动。
- 若某步仅部分完成（如只改了部分涉及文件），在同一阶段内补全，不进入下一步。
- 全部步骤执行完后，进入 Phase 3。

---

## Phase 3：改动点核对与补充

- 使用 Phase 1 中整理的**改动点清单**（5.x 涉及文件 + 7 产出）逐项核对：
  - 每个文件是否已按方案修改（路径、导出、关键逻辑与方案一致）。
  - 方案中提到的重定向、路由名、query、class 名、CSS 变量、主题配置等是否全部落实。
- **若发现遗漏**：
  - 列出遗漏项（文件 + 方案中的具体要求）。
  - 按方案补全代码或修改，直到清单全部勾选。
- **若核对无误**：进入 Phase 4。

---

## Phase 4：单测与验证

- 根据项目类型执行：
  - **前端**：若有 `frontend/package.json`，执行 `npm run build`（或 `npm run test` 若有单测脚本）；若有 lint，执行 `npm run lint`。
  - **后端/全栈**：执行项目根或各模块的构建/测试命令（如 `go build ./...`、`go test ./...` 或文档中约定的命令）。
- 若构建或测试失败：根据报错修复，然后重新执行本 Phase，直到通过。
- 若项目无自动化测试或构建脚本：做最小可行验证（如关键路由可访问、关键接口可调用），并在通知中说明「未执行自动化单测」。

---

## Phase 5：通知用户与构建通识

- 当 Phase 3 核对通过且 Phase 4 验证通过后，向用户明确说明：
  - **实现已完成**：已按技术方案「7. 开发步骤」逐步执行，并完成改动点核对与补充。
  - **验证结果**：单测/构建/ lint 结果（或说明未执行自动化测试的原因）。
  - **执行主体为「人」的步骤**：若有，列出并提醒用户自行完成（如联调、发布、配置等）。
- 若在实现过程中遇到方案与现有代码冲突或需求歧义，在通知中简要列出，并建议回到需求或方案文档做对焦。
- **构建通识**：实现完成后，按 [self-optimization](.cursor/skills/self-optimization/SKILL.md) 技能中「构建通识」流程，将本次 feature 的入口、谁调用、使用目的、依赖服务/应用、关键设计原因等补充到 `knowledge/common.md`。

---

## 约定与注意

- **术语**：技术方案文档中的「开发步骤」= 本技能中的「步骤」；「涉及文件」= 改动点；「产出」= 该步应产生的文件或变更。
- **不猜测**：方案未写明的行为不擅自扩展；若必须做假设，在通知中说明。
- **子 agent**：仅对方案中明确允许并行的步骤使用子 agent 并发；子 agent 任务描述中需包含步骤编号、内容简述、涉及文件与方案章节引用，以便产出一致。
